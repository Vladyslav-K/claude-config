# Опис пул реквеста

## Аргументи від юзера
$ARGUMENTS

**Як читати аргументи:**

- `/pr-description` - описати всі зміни поточної гілки відносно базової; ключ задачі взяти з назви гілки або комітів.
- `/pr-description APE-364` - описати тільки зміни, що стосуються цієї задачі.
- `/pr-description APE-364 APE-371` - одразу кілька задач в одному PR; кожна задача - окремий блок у розділі "What was done".
- `/pr-description APE-364 base=develop` - явно вказана базова гілка.
- `/pr-description APE-364 тільки фронтенд-частину, бекенд у іншому PR` - обмеження скоупу словами.
- `/pr-description APE-364 api на :3000, web на :5173, тестові юзери в seed` - контекст для розділу "How to test".
- `/pr-description APE-364 include uncommitted` - додати ще не закомічені зміни робочого дерева.

Аргументи - обовʼязкові інструкції: ключі задач визначають фільтр змін, контекст потрапляє в текст, обмеження скоупу вирізає решту з опису.

## Результат

Один файл `.project-meta/files/pr-description-<keys>.md` у форматі з розділу "Шаблон" нижче. Юзер копіює його вміст у поле description на GitHub сам.

**Імʼя файла:**

- один ключ: `pr-description-ape-364.md` (ключ у нижньому регістрі);
- кілька ключів: `pr-description-ape-364_ape-371.md` (у порядку, як їх передав юзер);
- ключа немає ні в аргументах, ні в гілці, ні в комітах: `pr-description-<slug-гілки>.md`, де slug - назва гілки в нижньому регістрі з `/` заміненим на `-`.

Якщо файл із таким імʼям уже існує - прочитай його, тоді перезапиши. Якщо теки `.project-meta/files` немає - створи її через `mkdir -p`.

**Мова файла - англійська**, бо це текст для GitHub. Це свідоме виключення з правила про українські .md-звіти. Чат-звіт для юзера - українською, як завжди.

**Git - тільки читання.** Скіл не створює й не редагує PR (`gh pr create`, `gh pr edit`), не комітить і не пушить. Він лише читає гілку і пише файл.

## Кроки виконання

### 1. Визнач межі PR

Усі команди нижче read-only.

1. Поточна гілка: `git rev-parse --abbrev-ref HEAD`.
2. Базова гілка, у порядку пріоритету: аргумент `base=` → `gh pr view --json baseRefName,title,url` (якщо PR уже існує і `gh` доступний) → `git symbolic-ref refs/remotes/origin/HEAD` → перша наявна з `develop`, `main`, `master`. Вибір базової гілки назви у чат-звіті як припущення, якщо він не був заданий юзером.
3. Точка розгалуження: `git merge-base <base> HEAD`.
4. Коміти PR: `git log --format='%h %s%n%b' <merge-base>..HEAD`.
5. Файли PR: `git diff --stat <merge-base>..HEAD`, потім повний `git diff <merge-base>..HEAD`. Великий диф читай пофайлово (`git diff <merge-base>..HEAD -- <path>`), а не обрізай.
6. Робоче дерево: `git status --porcelain`. Незакомічені зміни в опис не включай, окрім випадків, коли юзер сказав `include uncommitted` або гілка взагалі не має комітів попереду бази. Наявність незакомічених змін назви у чат-звіті.

### 2. Визнач ключі задач і відфільтруй зміни

Ключ задачі - патерн `[A-Z][A-Z0-9]+-\d+` (APE-364, PROJ-12). Шукай його в аргументах, потім у назві гілки, потім у повідомленнях комітів.

Якщо юзер передав конкретні ключі, а в гілці є коміти інших задач:

- залиш тільки коміти, у повідомленні яких є потрібний ключ; файли для дифу - обʼєднання файлів цих комітів (`git show --stat --format= <hash>`), диф - `git diff <merge-base>..HEAD -- <files>`;
- якщо файл чіпали і потрібні, і сторонні коміти - опиши лише ту частину, яка стосується задачі, і назви цей файл у чат-звіті як спірний;
- якщо коміти не позначені ключами і розділити зміни неможливо - зупинись і запитай юзера, які файли чи теки належать до задачі. Не вгадуй.

### 3. Збери контекст для змісту

Опис пишеться з коду, а не з памʼяті про задачу. Прочитай:

- диф повністю - кожен файл, а не тільки `--stat`;
- постановку задачі, якщо вона є в проєкті: `.project-meta/tasks/tasks.md`, `.project-meta/tasks/plan/*.md`, `.project-meta/tasks/session-tasks.md` - звідти беруться вимоги, acceptance criteria, посилання на PRD і дизайн, які пояснюють рішення;
- проєктний `CLAUDE.md`, README, `.env.example`, конфіг dev-сервера - звідти беруться реальні порти, URL і передумови для розділу "How to test";
- сусідній код там, де диф сам себе не пояснює (навіщо змінено, що було раніше).

Кожен ідентифікатор, шлях, порт і URL, який потрапить у текст, має існувати в репозиторії або в аргументах юзера. Що не знайшов - не вигадуй: напиши загальніше ("the local API from `.env.example`") і назви прогалину в чат-звіті.

### 4. Напиши файл за шаблоном

Прочитай `references/example-ape-364.md` - це еталон тону, глибини і структури. Пиши так само.

**Заголовок** - `## KEY: short title`. Title - перелік того, що зʼявилось, іменниками через кому, без "Added"/"Implemented". Кілька ключів - `## APE-364, APE-371: ...`. Якщо PR уже існує і має змістовну назву - узгодь title із нею.

**What was done** - згрупуй зміни за смисловими областями, не за файлами і не за комітами. Кожна група - жирний рядок `**Area name (\`path/one.ts\`, \`path/two.tsx\`)**` і 1-4 булети під ним. Булет описує поведінку і рішення, а не факт правки: не "added `SectionRoute` component", а що робить гейт, коли сесія не має секції. Реальні імена функцій, типів, роутів і файлів - у бектиках. Обовʼязково назви: що видалено разом із усіма використаннями; що зроблено за дизайном або PRD і де від них свідомо відступили; що змінилось у поведінці для юзера. Кілька задач - кожна починається зі свого підзаголовка `**APE-371**` перед групами.

**How to test** - абзац `Prerequisites:` з реальними портами, URL, ролями і даними, потрібними для перевірки, потім нумерований список. Кожен крок - `**Name**: what to do. Expect ...`. Кроки пише той, хто прочитав код, для того, хто код не читатиме: тестер має пройти їх без здогадок. Покрий кожну роль або стан, який видно в дифі (кожна гілка `if` по ролі, кожен пустий стан, пряме відкриття URL, кнопки назад, мобільний вʼюпорт, якщо він зачеплений), а не лише щасливий шлях.

**Notes and known limitations** - булети про те, що ревʼюер має знати наперед: свідомі відступи від дизайну чи старої поведінки; плейсхолдери й заглушки; що є лише UX-захистом, а реальна перевірка на бекенді; що перенесено в наступну задачу (з ключем); мертвий код, залишений до рішення; поведінка крайніх випадків за задумом. Порожній розділ не залишай - якщо обмежень справді немає, напиши одним рядком, що їх немає.

**Стиль:** звичайна проза, англійська, без емодзі, без тире як розділових знаків (двокрапка або кома), без заголовків нижче `###`, без чеклістів `- [ ]`, без згадок про AI, скіл або процес написання. Обсяг визначає диф, не шаблон: маленький PR - короткий текст, без роздування.

### 5. Звір файл з дифом перед звітом

1. Пройди `git diff --stat` файл за файлом: кожна зміна або покрита якимось булетом, або свідомо пропущена як тривіальна (форматування, перейменування без зміни поведінки). Пропущене з інших причин - додай.
2. Кожен ідентифікатор у бектиках перевір `Grep` по репозиторію. Не знайшовся - виправ або видали.
3. Кожен крок тестування має спиратись на поведінку, яку ти бачив у коді. Крок, який ти дописав "бо логічно", - видали або перевір по коду.
4. Порти й URL звір із конфігами проєкту або аргументами юзера.

### 6. Чат-звіт юзеру

Українською, коротко:

- шлях до створеного файла;
- що не вдалося підтвердити з коду і що варто перевірити перед копіюванням у GitHub (передумови тестування, порти, назви ролей);
- припущення: базова гілка, ключ задачі, спірні файли з кроку 2, незакомічені зміни;
- одне речення про те, що охоплює опис (скільки комітів, файлів, які області).

Вміст файла в чат не дублюй - юзер відкриє файл.

## Шаблон

```markdown
## KEY-123: short title, noun phrases, comma separated

### What was done

**Area name (`path/to/file.ts`, `path/to/other.tsx`)**

- What the code now does and why, with real identifiers in backticks.
- What was removed together with every usage, if anything.

**Another area (`path/to/file.tsx`)**

- Behaviour, decision, reference to design or PRD where it applies.

### How to test

Prerequisites: real services, ports, roles and data needed for the run.

1. **Step name**: what to do. Expect what the tester should see.
2. **Step name**: what to do. Expect ...

### Notes and known limitations

- Deliberate deviations, placeholders, UX-only guards, work deferred to KEY-124, code left in place pending a decision.
```

## Крайні випадки

- **Немає різниці з базовою гілкою і немає незакомічених змін** - повідом юзера і зупинись, файл не створюй.
- **Гілка ще без комітів, але є зміни в робочому дереві** - опиши робоче дерево (`git diff HEAD`, нові файли з `git status`), назви це в чат-звіті.
- **Кілька задач без ключів у комітах** - запитай юзера, як розділити, до написання.
- **Юзер просить описати задачу, слідів якої в гілці немає** - скажи це прямо, не пиши опис із памʼяті про те, що "мало бути зроблено".
- **`gh` недоступний або репозиторій без remote** - пропусти крок з PR і remote HEAD, іди далі за локальними гілками.
