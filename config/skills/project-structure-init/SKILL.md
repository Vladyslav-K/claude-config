# Інціалізація структури нового проєкту

## Додатковий контекст від юзера

$ARGUMENTS

**Аргументи головніші за дефолти цього скіла.** Читай їх як уточнення до всього нижче:
стек («react + vite», «next app router», «remix»), обсяг («лише каркас папок, без коду»),
особливості («auth через cookie, бекенд уміє», «i18n не потрібен», «додай vitest»),
або пряме перевизначення («state через zustand, не context»).
Якщо аргументи суперечать дефолту - виконуй аргументи і познач розбіжність у звіті.
Якщо аргументів немає - працюй за дефолтами й запитай стек, якщо його не видно з репо.

Приклади:

- `/project-structure-init` - за дефолтами, стек визначається з `package.json`.
- `/project-structure-init react + vite, react-router, tanstack query` - задає стек прямо.
- `/project-structure-init тільки дерево папок і конфіги, код не пиши` - обмежує обсяг.
- `/project-structure-init auth через httpOnly cookie, бекенд уміє` - скасовує
  localStorage-компроміс.
- `/project-structure-init без i18n, додай vitest` - вимикає/додає секції.

## Що робить цей скіл

Розгортає в новому (або майже порожньому) проєкті **єдиний архітектурний каркас**, який
не залежить від фреймворка: дерево `src/`, правила «що куди кладеться», конвенції неймінгу,
шар доступу до API, базові скрипти й конфіги.

**Порядок роботи:**

1. Визнач стек: прочитай `package.json` (фреймворк, роутер, data-fetching, стилі, менеджер
   пакетів за lock-файлом). Якщо репо порожнє - запитай юзера, який стек.
2. Звірся з `references/structure-tree.md` - там повне дерево й мапінг шарів на фреймворки.
3. Створюй **лише ті папки, які одразу наповнюються**. Порожні теки-заготовки не створюй -
   вони гниють. Виняток: якщо юзер прямо попросив «розгорни весь каркас наперед».
4. Базові файли шару API, env, провайдерів - за шаблонами з `references/api-layer.md`.
5. Скрипти, prettier, tsconfig-aliases, eslint - за `references/setup-checklist.md`.
6. Патерни стану, форм, станів завантаження, i18n, тестів - за `references/patterns.md`
   (читай той файл лише коли реально пишеш відповідний код).

**Чого цей скіл не робить:** не обирає дизайн-систему, не верстає, не ставить пакети без
погодження, не створює тести без запиту. Дефолтні конвенції коду (неймінг файлів, спосіб
оголошення компонентів) - у скілі `project-defaults`, цей скіл їх не дублює, а доповнює.

## Каркас: layer-first

Верхній рівень `src/` - **шари**. Домени живуть **усередині** шарів.

```
src/
├── app/ | pages/     роутинг-шар: тонкі сторінки, лише композиція
├── api/              доступ до бекенду: клієнт, сервіси, DTO
├── components/       вся верстка: ui / layout / views / <domain>
├── config/           env і статичний конфіг рантайму
├── constants/        доменні константи, мапи, лейбли
├── contexts/         React-контексти (UI і сесійний стан)
├── data/             статичний контент, що їде в бандл
├── hooks/            hooks/api (серверні дані) + доменні/UI-хуки
├── i18n/             конфіг + локалі (якщо є переклади)
├── lib/              підсистеми з побічними ефектами
├── providers/        композиція провайдерів застосунку
├── routes/           константи шляхів і правила доступу
├── types/            типи домену застосунку
└── utils/            чисті функції без стану
```

Повне дерево з підпапками, приклади вмісту й мапінг на Next / Vite - у
`references/structure-tree.md`.

### Дерево рішень «куди покласти файл»

Питай по порядку, перша відповідь «так» - це і є місце:

1. Це JSX / верстка? → `components/` (далі: примітив без домену → `ui/`; каркас застосунку
   → `layout/`; ціла сторінка → `views/`; інакше → `components/<domain>/`).
2. Це виклик бекенду або форма його відповіді? → `api/`.
3. Це React-хук? → серверні дані → `hooks/api/`; інакше → `hooks/`.
4. Це React-контекст? → `contexts/`.
5. Це функція **з побічним ефектом** (читає storage, тримає сінглтон, говорить із SDK,
   лізе в `window`)? → `lib/`.
6. Це функція **без побічних ефектів** (той самий вхід → той самий вихід)? → `utils/`.
7. Це значення, а не логіка? → env → `config/`; доменна мапа/лейбли/enum-подібне →
   `constants/`; великий статичний контент → `data/`.
8. Це тип? → форма бекенду → `api/types/`; інакше → `types/`.
9. Це шлях або правило доступу? → `routes/`.

Якщо файл не пасує нікуди - це сигнал, що в ньому змішані дві відповідальності. Розділи його,
а не створюй нову теку на верхньому рівні.

## Правила по шарах

### `api/` - тільки транспорт

- `api/config/http-client.*` - інстанс(и) клієнта, base URL з `config/env`, інтерцептори:
  прикріпити токен, обробити 401 з дедуплікованим refresh.
- `api/services/<domain>.service.ts` - об'єкт із методами. Метод = URL + generic-тип
  відповіді + `return data`. **Ніякої бізнес-логіки, ніякого React.** Кілька дрібних
  service-об'єктів в одному доменному файлі - нормально.
- `api/types/<domain>.ts` - DTO **точно у формі бекенду**. Якщо є swagger - це синхронізований
  шар, руками не переписується (див. скіл `sync-swagger`). Не «підправляй» DTO під потреби UI:
  мапінг у зручну форму - робота хука або `utils`.
- Клієнт експортується з `api/index.ts`; DTO - через barrel `api/types/index.ts`.
- Другий ізольований клієнт створюй лише коли в застосунку **справді інша сесія**
  (публічний потік із власним токеном), а не «щоб було».

### `hooks/api/` - серверні дані

Один файл на домен: `hooks/api/use-<domain>.ts`. Усередині - **фабрика query-ключів**
(`<domain>Keys` з `all` і функціями-вітками), потім queries, потім мутації з інвалідацією.
Ключі живуть тут, а не в `api/`, бо це кеш-шар клієнта, а не транспорт. Шаблон -
`references/api-layer.md`.

### `components/` - один UI-набір

- `ui/` - примітиви без знання домену (button, input, select, dialog, badge). Один набір
  примітивів на проєкт. **Ніяких паралельних наборів** типу `ui/` + `new-ui/` + `redesign/ui/`.
- `layout/` - shell: sidebar, top-bar, mobile drawer, footer.
- `views/` - page-level композиції: `<name>-view.tsx`. Сюди йде вся верстка сторінки.
- `<domain>/` - доменні компоненти (`surveys/`, `employees/`, `academy/`).
- Компонент, що виріс, - це **папка**: `<name>/<name>.tsx` + `index.ts` (barrel) + parts
  (`<name>-row.tsx`, `types.ts`, `utils.ts`).
- Іконки - `.svg` у теці іконок, підключені як компоненти (SVGR або аналог). Raw inline-SVG
  у JSX і raw `style={{}}` - заборонені.

### `app/` | `pages/` - тонкий роутинг

Сторінка робить рівно три речі: читає параметри роуту, тягне дані хуками, віддає їх у view.
**Верстка в сторінці не живе.** Якщо сторінка переросла ~60 рядків або в ній з'явилась
розмітка складніше за один wrapper - виноси у `components/views/`.

### `lib/` vs `utils/` - критерій побічних ефектів

- `lib/` - **підсистеми й сінглтони, що торкаються зовнішнього світу**: auth (контекст сесії,
  сховище токенів), доступ до storage, інстанс query-client, конфіг i18n, аналітика, обгортки
  над SDK. Групуй підпапками: `lib/auth/`, `lib/storage/`.
- `utils/` - **чисті функції**: форматування, робота з датами й числами, парсинг і валідація
  URL, guard-функції, `cn`/classnames-хелпер. Той самий вхід завжди дає той самий вихід,
  не читає глобалів, не пише нікуди.
- Доменні мапи й лейбли (`statement-labels`, `canonical-drivers`) - **не в `lib`**, а в
  `constants/`. Це дані, а не підсистема.

Тест на сумнів: якщо функцію можна викликати в тесті без жодного мока - це `utils/`.

### `config/` - єдине місце читання env

Уся робота з `process.env` / `import.meta.env` - **в одному файлі** `config/env.ts`.
Решта коду імпортує звідти типізовані значення. Це і гігієна, і головний шматок
фреймворк-незалежності: `NEXT_PUBLIC_*` vs `VITE_*` різняться рівно в цьому файлі.
Відсутні обов'язкові змінні - падати на старті з понятною помилкою, а не тихо підставляти
дефолт. Шаблон - `references/api-layer.md`.

### `routes/` - єдине джерело правди для шляхів

Константи/білдери шляхів, мапа «роль → домашній роут», правила доступу. Ніяких хардкоджених
рядків `'/executive/home'` у розкиданих компонентах - лише імпорт із `routes/`.
Для Next це шар **поверх** файлового роутингу (навігація й гарди), для react-router - ще й
джерело конфігурації самих роутів.

### `data/` - статичний контент, моки окремо

`data/` - те, що реально їде в бандл: конфіги доменів, тексти згоди, набори кроків.
Тимчасові моки - **тільки** в `data/mocks/` і з коментарем-маркером, що це тимчасово.
Мок, який ніхто не помітив, - це майбутній продакшн-баг.

### `types/` vs `api/types/`

`api/types/` - форма бекенду. `types/` - типи **домену застосунку**: те, чим оперує UI,
власні enum-подібні структури, ролі, локалі. Не дублюй одне поняття у двох шарах: якщо UI
потрібна інша форма, оголоси її як окремий тип у `types/` і зроби мапер у `utils/`.

## Barrel-політика

- **Barrel = на рівні однієї папки-компонента/модуля.** `components/ui/select/index.ts`
  експортує свій `Select` - це добре.
- **Кореневих мега-barrel'ів не робити.** `hooks/index.ts` із `export *` по 35 файлах
  означає, що імпорт одного хука тягне граф усього API-шару, псує tree-shaking і легко
  народжує циклічні залежності. Імпортуй адресно: `@/hooks/api/use-surveys`.
- Barrel реекспортує **лише свою папку**. Реекспорт із чужого шару («щоб зручніше») -
  причина циклів.
- Alias `@/*` → `src/*` обов'язковий; відносні шляхи глибше `./` не використовуй.

## Неймінг

- Файли й теки - `kebab-case`: `survey-list.tsx`, `use-surveys.ts`, `company-labels.ts`.
- Суфікси за роллю файлу: `*.service.ts`, `*-view.tsx`, `*-context.tsx`, `use-*.ts`,
  `*.types.ts` або `types.ts` усередині папки модуля.
- Компоненти - `PascalCase`, хуки - `useCamelCase`, константи - `UPPER_SNAKE_CASE`.
- DTO-типи - з суфіксом форми бекенду (`SurveyResponseDto`, `SurveyCreateDto`,
  `SurveyListParams`) - видно, що це контракт, а не внутрішній тип.
- Одне поняття - одне ім'я в усіх шарах: `surveys.service.ts` ↔ `api/types/surveys.ts` ↔
  `hooks/api/use-surveys.ts`.

### Правило «префікс → папка»

Як тільки в плоскій теці набралось **5+ файлів з одним префіксом** (`admin-home-*`,
`organisation-upload-*`) - це вже не файли, це модуль. Заводь папку з barrel'ом. Інакше
через півроку в теці 60 файлів і префікс замінює структуру.

## Скрипти й конфіги (обов'язковий мінімум)

Деталі й точні команди під різні фреймворки - `references/setup-checklist.md`.

- **`format`** - prettier `--write` по всьому проєкту. Референс-конфіг `.prettierrc.json`
  наведений у `references/setup-checklist.md` - копіювати як є, він однаковий у всіх проєктах.
- **`check-errors`** - `lint` + `typecheck` однією командою (лінтер проєкту + `tsc --noEmit`).
  Ці дві команди - гейт завершення будь-якої задачі, тому вони мають існувати з першого дня.
  **Лінтер не вгадуй:** дивись `package.json`. Next-шаблони йдуть з eslint, свіжі
  `create-vite` React-шаблони - з **oxlint** (там `"lint": "oxlint"`, і `typecheck` треба
  додати самому - `vite build` типи не перевіряє). Наявний лінтер не міняється на інший без
  прямої вказівки юзера.
- **`dev:clean`** - dev-сервер із попереднім прибиранням кешу бандлера (Next: `rm -rf .next`;
  Vite: `rm -rf node_modules/.vite`). Економить години на «зміну не видно, а код правильний».
- Alias `@/*` у tsconfig **і** в конфігу бандлера (Vite потребує обох; Next бере з tsconfig).
- `.env.example` у репо з усіма ключами й **без значень**. Реальні `.env` - у `.gitignore`.

## React Compiler - підключати, якщо стек дозволяє

**Правило: якщо це React і конфіг бандлера/фреймворка дозволяє React Compiler - вмикай його
на старті проєкту.** На старті це одна правка конфігу; через півроку це аудит сотні
компонентів на ручну мемоізацію.

Дозволяє - означає, що виконані всі три умови:

1. Це React-проєкт (не Vue/Svelte/Solid).
2. React 19+, **або** React 17/18 разом із пакетом `react-compiler-runtime` і опцією
   `target: '17' | '18'` (підтверджено: доки React, `reference/react-compiler/target.md`).
3. Бандлер має точку входу для компілятора: Next.js (`reactCompiler: true`), Vite через
   `@vitejs/plugin-react` + babel-плагін, Metro, Rsbuild. Якщо стек екзотичний і точки
   входу немає - **не ламай білд заради компілятора**, просто зафіксуй це у звіті.

Команди встановлення й точні конфіги під кожен стек - у `references/setup-checklist.md`,
розділ «React Compiler». Перед підключенням у незнайомій версії фреймворка звірся з
актуальними доками через `ctx7` - назва опції змінювалась (у Next вона переїхала з
`experimental.reactCompiler` на top-level `reactCompiler`).

**Наслідок для всього коду проєкту (важливіший за саме підключення):**

- Компілятор мемоізує сам → **ручна мемоізація заборонена**: жодних `useCallback` /
  `useMemo` / `React.memo` «про всяк випадок». Пиши звичайні `const handleX = () => {}`.
- Це фіксується лінтом, а не домовленостями - але **механізм залежить від лінтера**:
  на eslint це `eslint-plugin-react-hooks` (містить правила компілятора) плюс бан
  `useCallback`/`useMemo` через `no-restricted-syntax`; на oxlint `no-restricted-syntax`
  **не існує**, тому бан ставиться на імпорт хуків через `no-restricted-imports`. Точні
  конфіги обох варіантів - у `references/setup-checklist.md`.
- Правила хуків стають жорсткішими: компілятор оптимізує лише той компонент, який відповідає
  правилам React. На eslint помилка правила компілятора = «цей компонент не оптимізовано»;
  на oxlint такого сигналу немає взагалі - це різниця, про яку треба знати, а не вважати,
  що лінт усе покриває.
- У `CLAUDE.md` проєкту (якщо створюється) це має бути записано явно - інакше наступна сесія
  за звичкою напише `useMemo`.

Якщо компілятор **не** підключений - ручна мемоізація легітимна, і бан ставити не треба.
Стан «увімкнений / ні» має бути однозначно видно з конфігу, а не з'ясовуватись експериментом.

## Security-baseline шару api/auth

Це мінімум, який закладається одразу, бо потім переробляти дорого.

- **Токени сесії.** Цільовий стан - `httpOnly` + `Secure` + `SameSite` cookie, які ставить
  бекенд: тоді XSS не дістане сесію. Практична реальність: dev-сервер працює по `http`, де
  `Secure`-cookie не ставиться, тому **на час розробки токени тримаємо в `localStorage`** -
  іншого виходу немає. Тому: пиши сховище токенів **як ізольований модуль**
  (`lib/auth/token-storage.ts`) з інтерфейсом `get/set/clear`, щоб перехід на cookie був
  заміною одного файла, а не правкою пів проєкту. Ніде, крім цього модуля, `localStorage`
  з токенами не згадується. У звіті про старт проєкту явно фіксуй: «зараз localStorage,
  цільове - httpOnly cookie».
- **Секрети.** У клієнтський бандл не потрапляє нічого секретного: `NEXT_PUBLIC_*` /
  `VITE_*` видимі всім користувачам. Ключі сторонніх сервісів, що вимагають приватності, -
  тільки через власний бекенд-прокси.
- **Редіректи.** Redirect за значенням із URL/query - лише через allow-list або перевірку
  «це відносний шлях». Хелпер типу `utils/safe-url.ts` - з першого дня.
- **Клієнтські guard'и - це UX, не захист.** Роль зі стору вирішує, що показати; хто що
  може - вирішує бекенд.
- **Зовнішні посилання** - `target="_blank"` завжди з `rel="noopener noreferrer"`.
- **Ніякого `dangerouslySetInnerHTML`** без санітизації.

## Типові граблі (перевірені на реальному проєкті)

Це не абстрактні поради - це те, що коштувало часу:

- **Два паралельні UI-набори.** Редизайн зробили в новій теці, стару не прибрали - і тепер
  у кожній задачі питання «з якої теки брати кнопку». Редизайн робиться **на місці**.
- **`lib/` як смітник.** Без критерію «побічні ефекти» туди за пів року стікається все:
  утиліти, доменні мапи, конфіги, підсистеми.
- **Мега-barrel `hooks/index.ts`.** Зручно один раз, потім - цикли й повільний бандл.
- **60 файлів плоско в одній теці**, розділені префіксом імені замість папок.
- **`process.env` у кількох місцях** - переїзд на інший фреймворк або зміна назви змінної
  стає полюванням по репо.
- **Моки в продакшн-теці `data/`** - їдуть у бандл і рано чи пізно показуються юзеру.
- **DTO, «підправлені» під UI** - наступна синхронізація зі swagger їх затирає.
- **Сторінка, що верстає сама** - копіпаста між ролями замість одного view з props.

## Гейт завершення

1. Створені лише ті папки, які наповнені; порожніх заготовок немає.
2. `format` і `check-errors` існують у `package.json` і **проходять чисто** на свіжому каркасі.
3. `.prettierrc.json` = референс-конфіг зі `references/setup-checklist.md`.
4. Alias `@/*` працює (перевірити реальним імпортом, не на віру).
5. `.env.example` без значень; реальні `.env` у `.gitignore`.
6. React Compiler: або підключений і бан ручної мемоізації стоїть у лінті, або у звіті
   названа причина, чому стек його не дозволяє.
7. У фінальному звіті: де зараз токени й що цільове (localStorage → httpOnly cookie), які
   рішення прийняті як припущення, і що юзер має перевірити сам.
